# 阶段八：C++ 高性能精确在线评测

## 1. 目标与结论

Python 在线评测已证明压缩索引能保持 100% 距离正确并减少展开节点，Chicago 的墙钟收益则受到
shortcut 扫边开销限制。本阶段不做跨语言的“Python 压缩 vs. C++ 原图”比较，而是在同一 C++ 可执行程序内同时实现
原图双向 Dijkstra 与压缩查询，判断搜索工作量减少能否转化为真实在线加速。

最终结论为：

- **Porto 实现真实加速**：14 个方法—窗口组合中 13 个平均耗时下降。Z0 当前/未来为
  `-6.51% / -7.48%`，G4 三种子均值为 `-6.41% ± 0.72% / -8.90% ± 2.10%`。
- **Chicago 的平均收益略有局限性**：14 个组合的平均耗时均略有增加。Z0 尽管减少约 21.5%～21.9% 展开节点，
  扫描边数却增加 26.6%～27.5%，平均耗时为 `+3.57% / +0.72%`。
- **Chicago 的长查询尾部有改善**：14 个组合中 11 个 P95 下降。Z0 当前/未来 P95 为
  `-3.13% / -3.85%`，P50 则增加 `+13.54% / +10.04%`，显示优势更集中于长查询。

因此，C++ 性能增强确认了 Porto 的真实在线加速，也证明 Chicago 的瓶颈不只是 Python：当边界
shortcut 过密时，“展开节点减少”不等于“扫描边减少”，更不保证平均墙钟加速。

## 2. 实现与精确语义

C++20 实现位于 `cpp/aic_cpp_online_benchmark.cpp`，保持 Python 冻结协议：

1. 从已有 `hard_disjoint` 选区读取 K=18 区域，不重新排序或选型；
2. 删除区域内部节点，用区域内受限 Dijkstra 精确物化边界间 shortcut；
3. 内部起点沿正图、内部终点沿反图仅在所属区域内接入边界；
4. 端点缓存容量为 0，不用预计算结果换取在线耗时；
5. 原图与压缩查询共用 C++ 数据结构、距离工作区和 `steady_clock`。

高性能实现将 OSM 节点映射为连续整数，复用距离/访问代际数组和优先队列存储，并主动清理陈旧
堆项。这会使极少数等长路径的展开 tie 顺序与 Python 不同，但两城最大平均差异仅
`0.065 节点/查询`，低于预设的 `0.1`；距离容差仍为 `1e-6`。

## 3. 固定计时协议

- 硬件：12th Gen Intel Core i7-12700H；
- 编译：GCC 16.1.1，`-O3 -DNDEBUG -march=native -std=c++20`；
- CPU affinity：固定 CPU 10，单线程；
- 每个方法、窗口固定 2,000 条查询；
- 先运行 1 轮距离/工作量审计，再预热 2 轮，最后正式计时 10 轮；
- 原图/压缩查询执行顺序按 `query_id + repetition` 奇偶交替；
- 两城正式计时共 560,000 个原图—压缩配对样本。

shortcut 数和内部节点必须与 Python 完全一致；平均展开节点每查询差异不超过 `0.1`。

Chicago 区域的边界与 shortcut 更多，压缩图在访问边界时扫描的邻接边显著增加。这使典型查询
承担一定额外开销，但长路径查询仍可因提前跨过大区域而降低 P95。下一个系统问题已从“换用 C++”精确收缩为
“如何在保持精确性的同时稀疏化边界 shortcut”。

## 6. 可成立的新论文口径

1. 在 Porto 上，训练自由 Z0 不仅提高选区质量并减少展开节点，还在同实现 C++ 配对中降低了
   6.5%～7.5% 平均在线耗时。
2. 跨城市的稳定主张是“精确且减少搜索展开”，不是“任意道路图均能平均加速”。
3. 展开节点、扫描边、shortcut 存储和 P50/P95 必须联合报告；只报展开节点会高估稠密边界图的
   平均墙钟收益。
4. 未来若继续系统研究，应做精确 shortcut sparsification、边扫描预算感知选区和尾延迟多目标，不再把
   Python 解释器当作唯一瓶颈。

完整产物位于 `results/cpp_online_benchmark/porto/` 和
`results/cpp_online_benchmark/chicago/`。
